# 一个游戏一个向量库 collection

每个游戏知识库对应一个独立的向量库 collection，而不是共用一个 collection 再用标量字段过滤。

这与主流建议相反：Qdrant 官方把"每个用户／文档建一个 collection"称为反模式；LightRAG 有一个已合并的 PR 专门从 collection 前缀迁移回共享 collection + 载荷过滤；Dust 的案例里近千 collection 导致查询要 5–10 秒，合并后降到 1 秒内。但那些案例都在**千级**规模——本项目面向若干款单机与网游，即便增长到几十个 collection 也远低于 Milvus 的 65536 上限，且 Dify 在 Milvus 上就是每个知识库一个 collection，是主流商业形态。

真正的收益是**生命周期**而非性能：知识库是用户创建、用户删除的产品对象，"删库即释放"比"条件删除"干净得多。

**代价**：跨游戏查询要扇出到 N 个 collection 再合并，且精排分数跨库不可比。当前每次查询都限定在单个游戏内，所以这两条不构成问题——**一旦要支持跨游戏查询，这个决定必须重新评估**。

**逃生舱**：每条记录仍冗余写入游戏标识字段，使将来合并为共享 collection 时无需重新解析语料。
