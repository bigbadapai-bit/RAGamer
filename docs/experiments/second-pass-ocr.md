# 实验：二次 OCR 能把多少图内文字拿回来

2026-09-13 · T12（#13）。T10 那张票量的是「**必须**依赖二次 OCR 的比例 = 100%」
（见 [`mineru-ocr.md`](./mineru-ocr.md)），并在「限制」一节把另一半留给了这里：
**二次 OCR 出来多少能用**。这个数查文档问不出来，只能真跑一遍。

**结论：22 张全部认出来了，没有一张是空的；字数 18–628，中位数 259，单张 4.4–11.7 秒
（CPU + onnxruntime），一轮 22 张共 174.7 秒。**

要连着 T10 那张表一起读，四处对照最要紧：

| 截图 | T10：MinerU 抽出的字数 | T12：二次 OCR 的字数 |
| --- | --- | --- |
| `12-30-06`（整页论坛帖截图） | **0** | **521** |
| `12-33-34`（纯文字截图） | 591 | 606 |
| `12-33-58`（纯文字截图） | 597 | 613 |
| `12-35-53` | 15 | 18 |

- **第一行就是这一层存在的理由**：MinerU 从那整张论坛帖上一个字都没给，二次 OCR 把
  标题、正文、漫画对白、十几条回复一起拿了回来。
- **后三行是反向核对**：MinerU 本来就抽得干净的那几张，二次 OCR 给的字数基本相同
  （591→606、597→613、15→18）。说明它不是在瞎补——换一个引擎认同一张图，量级对得上；
  差的那十几字是两个引擎认标题与页脚的口径不同，不是谁漏了内容。

## 怎么跑的

```bash
uv sync --extra ocr
uv run python tools/second_pass_ocr.py test_screen_shots --out docs/experiments/second-pass-ocr.md
```

- 素材就是 T10 那同一批 22 张截图——两次实验要能对着看，换一批就比不上了。
- 跑的是 `ragamer.ocr` 那个引擎本身，**不是另写一个识别**：实验的口径必须与生产那条路
  完全一致，否则量出来的数与线上无关。
- 逐张明细与汇总在文末，由脚本生成。**重跑会整份覆盖这个文件**，上面这几节要人工补回。

## 对 T12 实现的三点含义

1. **质量够用，不需要预处理。** 中位数 259 字，长图那一档（整页就是一个图片区域）
   拿回来的正是整页的文字。所以这一层不做放大、不做裁剪、不做二值化——T10 已经证明
   文字识别本身没问题，问题只在「整页被判成一张图」，换个引擎就够。
2. **时间要按分钟计。** 单张 4.4–11.7 秒（CPU），22 张一轮近 3 分钟。一份几十张图的资料
   导入时这是可感知的等待。这是本地 CPU 推理的代价——换 GPU 会快一档，但那是引擎配置的
   事，本项目没为它开配置（见下一条）。
3. **不设阈值。** T10 定下的是范围（每个 `type == "image"` 的条目都做，不挑大小图），
   没有定下任何阈值；这一轮也给不出「多少字算够」的依据——最少的那张（`12-35-53`，18 字）
   是真的只有那点内容，T10 从它身上也只抽出 15 字。照引擎默认值走，等有评测集再谈调参
   （docs/ARCHITECTURE.md §11）。

## 限制

- **只看了字数，没看质量**：认错的字、顺序错乱、竖排文字这几类都没量。用在检索上够用
  （字都在、能命中），但别拿它当逐字准确的抄录。逐张抽看过 `12-30-06`，正文可读，
  有个别繁体误认（「北回歸線」）与零散符号——不影响检索。
- 素材与 T10 同一批（22 张截图），**PDF 那条路没测**。
- 单次运行的时间点：2026-09-13。耗时随机器变，重跑一条命令即可复核。
